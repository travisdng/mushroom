# Mushroom v1.0.0

**Released:** 2026-09-18 · **Milestone:** 06 — Polish & packaging

> 1.0 does not mean finished. It means Mushroom installs cleanly, does not lose
> data, fails in ways you can understand, and is pleasant to use every day.
> That is the bar, and everything in this release is about meeting it.

## What's new

- **Quick Open** (`Ctrl+P`) — start typing a note's name and go straight to it.
- **Mushroom notices external edits.** Change a note in another editor and the
  list and index update. If the note is open and unmodified it reloads; if you
  have unsaved changes it asks rather than overwriting.
- **Diagnostics** (`Tools → Diagnostics`) — one screen with versions, paths,
  index health, AI status, token usage, and the log. `Copy Diagnostics`
  produces redacted text with no key, no note content, and no absolute paths,
  safe to paste anywhere.
- Every keyboard shortcut in the Help dialog now works, and the dialog lists
  nothing that does not.
- A first-run `Welcome to Mushroom` note, which is an ordinary note you can
  edit or delete.
- Documentation: shortcuts, search syntax (linked from the search panel), and
  troubleshooting.

## What got better

- **Error messages.** Fourteen failure paths were forced on the running app and
  the result of each written down in
  [`docs/error-audit.md`](https://github.com/travisdng/mushroom/blob/main/docs/error-audit.md) — a read-only file, a note changed
  underneath you with unsaved edits, a corrupt index, an endpoint that refuses
  connections, an expired certificate, a rejected key, a stream cut mid-answer.
  Each names the problem, says what to do, and keeps whatever you had typed.
  Technical detail is behind `Details…`. No raw Rust error text reaches the
  screen. Five more paths are listed in that document as **not** forced, with
  why and what the risk is — disk-full and a file locked by another process
  among them.
- **A panic in one operation no longer kills the app.** It becomes an ordinary
  error dialog, with the backtrace in the log. This was true in the tests and
  *not* true in the shipped build until this release: the release profile had
  `panic = "abort"`, so there was nothing for the guard to catch. See the
  error audit.
- **Performance.** Startup shows the window before scanning, so a large notes
  folder does not delay it. The note list is virtualised — 5,000 notes is
  about forty rows of DOM, not five thousand. Preview rendering is debounced at
  150 ms so typing in Split mode stays smooth. Idle CPU is effectively zero:
  no polling, no timers, and no background AI requests. The folder watcher used
  to wake twice a second whether or not anything had changed; it now sleeps
  until the filesystem says otherwise.
- **The installer.** Per-user install, no administrator rights, proper entry in
  Add/Remove Programs, Start-menu shortcut, and WebView2 installed if missing.

## What doesn't work yet

Deliberate, and worth stating plainly:

- **Keyword retrieval only.** Ask about "the machine that keeps falling over"
  when the note says "node pool terminating early" and it will not be found.
  Semantic and hybrid search is v1.1, and only if it measurably beats keyword
  search on real questions — see *What's next* below.
- **Windows only.** Nothing in the design blocks macOS or Linux; nothing has
  been tested there either.
- **The installer is unsigned.** Windows will warn that the publisher is
  unknown. Signing needs a certificate; the build is one environment variable
  and one config file away from producing a signed one when there is one.
- **The WebView2 bootstrapper has never run.** Every machine to hand already
  has the runtime — Windows 11 ships it — so the installer's
  `downloadBootstrapper` path is untested. The *detection* around it has been
  checked: the installer reads Microsoft's documented Evergreen Runtime key and
  correctly finds the installed version, which is exactly why the download
  never fires here. The download-and-install step itself is the one thing in
  the install nobody has watched work, and it cannot be forced on a machine
  where removing WebView2 would break Edge and Office.
- **No Windows account without developer tools has been used.** What that would
  mostly catch has been checked another way: the installed `mushroom.exe`
  imports only Windows system DLLs and the Universal CRT, which is part of
  Windows 10 and 11. There is no Visual C++ redistributable dependency — no
  `VCRUNTIME140.dll` — which is the usual way an app turns out to need
  something the developer's machine happened to have. The install is two files
  with no sidecar DLLs. What that check cannot see: libraries loaded at
  runtime rather than imported, and whatever the installer itself assumes.
- **No sync.** Mushroom is local-first and single-machine by design. Your notes
  are plain files, so any file-sync tool works — Mushroom just will not help
  resolve conflicts beyond asking before it overwrites.
- No mobile, no web, no sharing, no collaboration. Not planned.

## Numbers

Measured on the release build against 5,000 notes (9.9 MB of Markdown across
50 folders), on a 13th Gen Intel Core i5-13420H, 12 logical cores, 16 GB RAM,
SSD, Windows 11 Pro build 26200.

| Measurement | Target | Result |
|---|---|---|
| Cold start to a painted window | < 1.5 s | **1.20 s** |
| Warm start | — | **~0.11 s** |
| Open a note | < 100 ms | **0.2 ms** median, 1.1 ms worst |
| Keyword search, ordinary terms | < 100 ms | **1.7–7.5 ms** median, p95 ≤ 15.6 ms |
| Keyword search, a term in *every* note | < 100 ms | **86 ms** median, **137 ms** p95 |
| Quick Open over 5,000 notes | < 50 ms | **0.7–2.0 ms** |
| Idle memory | < 250 MB | **122 MB** |
| Idle CPU over 60 s | ~0% | **0.043%** |

Three things about that table are worth saying plainly.

**One target is missed.** A search term that appears in every single note takes
86 ms median and 137 ms at the 95th percentile, because the ranking has to
score every passage in the corpus before it can sort them. Ordinary searches —
where a term is in a few per cent of notes — are an order of magnitude inside
the target. A search that matches everything returns everything, so it is not a
search anyone runs deliberately, but it is over the line and pretending
otherwise would be easy and wrong.

**"Cold start" means a genuinely cold one** — first launch, nothing in the
page cache. Launching again is about a tenth of a second. Neither number waits
for indexing: the window is up and usable while 5,000 notes are scanned (6 s)
and indexed (6–9 s) behind it, and that only happens on a first run or after
the index is deleted.

**Idle memory is the private working set** across Mushroom and the six WebView2
processes it runs the interface in. Adding up the plain working set gives
399 MB, but that counts WebView2's shared runtime pages once per process;
122 MB is what Mushroom actually costs. Mushroom's own process is 13 MB of it.

**Typing frame rate is not in the table, because it was not measured.** There
is no frame counter in Mushroom and no honest way to count frames from
outside. What was found and fixed is more concrete: the preview was re-parsing
the entire note on every keystroke despite being debounced, because the
component reads the note context and a context consumer re-renders whether or
not its props changed. That work is gone. Typing in Split mode on a long note
showed no perceptible lag — which is an observation, not 60 fps.

The benchmark is reproducible: `scripts/make-corpus.mjs` is seeded, so anyone
gets the same 5,000 notes, and `src-tauri/tests/bench.rs` and
`scripts/bench.ps1` produce the table above.

## Upgrading

From 0.5.0: install over the top. Settings, notes, and the index are
preserved; any database migration runs on first launch. **This was tested by
actually doing it**, not by reasoning about it.

Uninstalling removes the program and its shortcuts. **It does not touch your
notes** — they are in your own folder and they stay there.

## Install

- `Mushroom_1.0.0_x64-setup.exe` — per-user, no admin rights.
- `Mushroom_1.0.0_x64_en-US.msi` — machine-wide.
- Unsigned; SmartScreen will warn. Do not disable SmartScreen — choose
  "More info" then "Run anyway" if you trust the build, or build it yourself
  from source.

## What's next

Two weeks of real use, writing down every question where search failed to find
a note you knew existed. If there are at least ten, that is the evidence for
spec 07 and semantic search. If there are not, keyword search is good enough
and the effort belongs somewhere else.

## Verified by

Everything below was done on the **installed** build, not a development run.

- **First run on an empty profile.** Starter folders created, the welcome note
  written *and opened*.
- **A note written, saved and found.** `File → New Note`, typed, `Ctrl+S`,
  correct frontmatter on disk, then searched for a word unique to it: one hit.
- **Quick Open**, the shortcut list, Diagnostics, the unconfigured AI panel and
  About, each seen on screen.
- **`Copy Diagnostics`** checked character by character: home folder replaced
  with `<user>`, notes root with `<notes>`, no key value, no note titles, no
  note content.
- **An external edit** appended from PowerShell reloaded in the open note.
- **Upgrade from 0.5.0 for real.** Installed 0.5.0, ran it against 5,000 notes,
  wrote a note through it, installed 1.0.0 over the top: one entry in Add/Remove
  Programs, settings and the 36 MB index intact, and the note written under
  0.5.0 still findable through the index 1.0.0 inherited.
- **Uninstall with 5,001 notes present.** Program, shortcuts and the Add/Remove
  Programs entry gone; notes, settings and index untouched, as the uninstaller
  said before it started.

**Not verified here:** configuring AI, asking a question and opening a source.
That needs live credentials and was done end to end in milestone 05 against a
real LiteLLM gateway and the real OpenAI API. No AI code changed in this
release. Also not verified: a Windows account with no developer tools, and the
WebView2 bootstrapper — see the gaps above.
